Case Study

Building a Lead Pipeline

A real, deployed integration project. A new lead in Airtable gets enriched with company data, routed by size, and pushed to the right Discord channel with nobody touching it in between. This page covers how it was built and how it works.

Built with Airtable, AbstractAPI, and Discord, running on a server hosted on Render.

How it came together

In the order it actually happened.

Plan

Scoping before writing any code

Before touching a keyboard, the shape of the integration got mapped out: what would trigger it, what would enrich the data, what would send the alert, and what each service's authentication would actually require. Airtable, AbstractAPI, and Discord cover three different auth models and two different trigger patterns between them, so this ended up testing more than one integration pattern instead of three API calls wearing different logos.

Build

One piece at a time, each proven before connecting it

Each integration point was built and tested on its own before touching anything else: the AbstractAPI client first, complete with retry logic and typed errors, then the Airtable webhook receiver, then the Discord alert client. None of it got wired into a single pipeline until every piece worked against the real service by itself, not a mock.

Debug

The lookup that always came back empty

The first real bug showed up the moment a live lead ran end to end: a request for Airbnb's domain came back reporting no company found, which was obviously wrong. AbstractAPI's own example documentation shows a field called name; the live API returns company_name. The code had been faithfully checking a field that never existed in a real response, so every successful lookup was silently misreported.

docs said: data.name API returns: data.company_name
Trust

Verifying who's actually calling

Airtable's webhook flipped the direction of trust. Instead of this server calling out with an API key, Airtable would be calling in, so the server had to prove each incoming ping genuinely came from Airtable and not just anyone who'd found the URL. The fix: an HMAC-SHA256 signature check on every request, verified before any real processing starts.

Ship

The first deploy broke immediately

The server runs on Render, and its build grabbed the newest available Node version on its own, which a database library's compiled native code hadn't caught up with yet, so the build failed outright. Pinning the exact version already tested locally fixed it in minutes, though it's the kind of failure that only shows up once code leaves a laptop.

Verify

Proving it, live, with real leads

A public dashboard reads real leads straight out of Airtable and shows them being enriched and routed within seconds, backed by a short server-side cache so any number of visitors cost the shared Airtable rate limit at most one real request every few seconds. Batches of test leads, big companies, small ones, and a personal email address with no company behind it, have gone through and landed in the correct bucket every time.

The flow, step by step

Everything starts with one event: someone adds a row to the Leads table. Everything after that is automatic.

Proven with a real batch, not just one example: five leads sent through at once landed in all three buckets. Netflix and Salesforce as enterprise (11,436 and 46,706 employees), Basecamp and Buffer as SMB (87 and 127 employees), and a plain @gmail.com address fell back to "manually qualify, no firmographic data found."

Airtable, where leads start and end up

source + writeback

Airtable holds the Leads table and plays two roles here: it triggers the whole pipeline, and it's where the results land afterward. When someone adds a row, Airtable can notify the server automatically through a webhook.

One catch: Airtable's webhook ping carries no data. It just says something changed on webhook X, and the server has to call back and ask what actually happened. That's the ping-then-pull shown as step 2 above.

Proving the ping is real
X-Airtable-Content-MAC: hmac-sha256=<signature> // computed from a secret only Airtable and the server know, // so anyone else who found the server's URL couldn't fake this

Airtable is the one initiating contact here, so the server has to verify the caller is really Airtable and not just whoever found the URL. That's a different problem from the other two services below.

AbstractAPI, what do we know about this company?

enrich

Given a domain like airbnb.com, AbstractAPI answers with whatever it knows: industry, headcount, location. The server pulls the domain straight out of the lead's email address.

Auth here is about as simple as it gets: one API key sent with every request, forever. No login, no expiry. A leaked key stays valid until someone manually rotates it.

Before spending a lookup
// AbstractAPI bills per request even when nothing is found, // so a clearly malformed domain is rejected locally first enrichCompany("not a domain") // rejected, no request sent
Real bug, caught by testing live

AbstractAPI's own example docs show a field called name. The live API returns company_name instead. The first version of this code checked for name, which is never there, so every single successful lookup was silently reported as "nothing found." It only surfaced because a real test lead for Airbnb came back empty, obviously wrong for a company that size.

Routing rules, the one part with no API at all

decide

This is just plain code: given what AbstractAPI found (or didn't), decide which Discord channel this lead belongs in and what a rep should do next. No network call, nothing that can time out or rate limit.

The actual thresholds
no company data found unknown "Manually qualify" found, 500+ employees enterprise "Route to AE for enterprise demo" found, under 500 (or unsized) smb "Send self-serve trial link"

Discord, where the sales team actually sees it

alert

Each Discord channel (#enterprise-leads, #smb-leads, #unknown-leads) has its own secret webhook URL. Posting a message there is one HTTP request to that URL, no login, no token exchange.

The URL itself is the credential. Anyone who has it can post to that channel, which is why it's treated like a password rather than a public setting.

Playing nice with rate limits
// Discord's 429 response tells you exactly how long to wait, { "retry_after": 1.3, "global": false } // so the server waits that long instead of guessing a delay

The glue, what keeps this from breaking quietly

infra

Every outside call can fail in ordinary ways: a dropped connection, a "slow down" response, a full quota. Rather than crashing, each service client sorts failures into two piles, worth retrying (a hiccup, a rate limit) and retrying won't help (bad credentials, a malformed request), and only retries the first kind, waiting a little longer each time.

There's also a small local ledger of which leads have already been fully processed. Airtable's notification can arrive more than once for the same change, so without this, a single lead could get double-alerted or double-enriched.

The live dashboard, watching it happen

demo

A small public page reads straight from Airtable and shows recent leads as they're enriched and routed: real data, updated every few seconds, no login required.

Two limits here matter: it only shows an email's domain, never the full address, and every request comes from a short-lived cache instead of hitting Airtable fresh each time.

Why the cache matters here specifically
